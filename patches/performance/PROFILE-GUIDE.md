# Как проверить остаток пика на PSPKVM, а не гадать по microbench

## Что уже известно, а что нет

Пользователь сообщил Perks / Lights Out → Rollcall: 1390 → 1060 мс без heap, затем **917 мс с heap**. Агент не воспроизводил эти числа на устройстве. Новый KVM-стенд подтверждает уменьшение цены конкретных операций, но не измеряет их долю в этих 917 мс.

Показатель `lag` в Game — максимум времени NPC-pass за примерно пятисекундное окно. Это **не время полного кадра**. Render и последующая сортировка не становятся частью NPC-таймера от того, что оптимизированы соседним патчем.

## 1. Контрольная и тестовая сборки

1. Сохранить рабочую heap-only сборку как контроль, не перетирать её единственной копией тестовой.
2. Взять тот же master `0716b47`/0003 и тот же save. Выбрать **одну** форму патчей, сначала выполнить `git apply --check`.
3. Консервативный старт — `conservative-after-heap.patch`: без memo 0011 и facing 0013, которые дали отрицательные контроли. Memory-вариант — альтернатива с ещё ≈35 KiB, не слой поверх обычного combined.
4. Не менять PSP CPU clock, режим VM/heap, разрешение, звук и графические настройки между сборками. Указать их вместе с результатом.
5. Для атрибуции отдельного патча держать LOGGING одинаковым: 0016 намеренно выключает его. Для сравнения целого пакета изменение logging допустимо, но тогда выигрыш нельзя приписать исключительно A*.

Одинаковый save не гарантирует одинаковые RNG/позиции после разного ожидания до перехода. Делать несколько сопоставимых прогонов и смотреть также число запросов/expansions; не выбирать только лучший единичный пик.

## 2. Отдельная диагностическая сборка

Наложить **0017-npc-lag-breakdown.patch** на выбранную сборку. Проверены применения к heap, полной серии и обоим conservative-пакетам. `LOGGING=false` сам по себе HUD не отключает; остальные настройки отображения статистики проекта должны оставаться включёнными.

```sh
git apply --check patches/performance/0017-npc-lag-breakdown.patch
git apply patches/performance/0017-npc-lag-breakdown.patch
```

У диагностического патча есть overhead: дополнительные currentTimeMillis для каждого персонажа/поиска и инкременты в expansion-loop. Это **elapsed wall time**, не sampling CPU profiler. Часы, GC, консоль и scheduler тоже могут влиять на длительность. Не сравнивать его lag напрямую с непрофилированными 917 как результат оптимизации.

## 3. Две строки одного и того же пика

| Экран | x=0 | x=40 | x=80 |
|---|---|---|---|
| **y=71** | AI ms | pathfind ms | NPC.tick ms |
| **y=79** | pathfind calls | false returns | A* expansions |

Все шесть чисел сохранены **из того же pass**, который дал текущий максимум `lag`, включая обновление при равном максимуме. Это не шесть независимых максимумов разных кадров. Сбрасываются вместе с lag примерно раз в пять секунд; фотографировать обе строки и исходный lag до следующего сброса.

**Pathfind вложен в AI: AI + pathfind + tick складывать нельзя.** Пример только для чтения, не реальный результат устройства: AI=600, path=450, tick=300 означает около 900 мс AI+tick, а не 1350. Разница с lag может содержать стоимость замеров/обхода/округления и прочую работу pass.

False означает не только «нет пути»: слишком короткий result buffer тоже возвращает false. 0018 уменьшает число вызовов/false/expansions именно за счёт убранного дубликата, а не за счёт пропуска обработки NPC.

## 4. Как использовать данные

- **Path близок к AI, AI велик:** смотреть 0004–0007, затем опциональный 0019 и false/calls. 0018 помогает только соответствующим failed caller-местам, не всем waypoint-запросам.
- **AI велик, path мал:** vision/zone/object проверки и остальная AI-логика важнее очередной heap-микроправки. Большой коэффициент выделенного vision-блока не доказывает, что блок доминирует в игре.
- **NPC.tick велик:** отдельно исследовать физику, lookup/collision, animation/звук и фактические allocations внутри tick. Текущие tile-оптимизации не измеряют этот участок.
- **NPC-pass стал мал, а FPS остался низким:** нужна отдельная отрисовочная/native/M3G диагностика, не вывод из NPC-таймера.
- **Calls/expansions заметно различаются между прогонами:** workload не одинаков; не приписывать всю разницу CPU-коду.

Даже если локальный метод ускоряется в s раз, ускорение целого pass зависит от его доли p: условная модель `1 / (1 - p + p/s)`. Нельзя подставить в неё коэффициенты разных helper-таблиц как будто они измеряли весь pass. Сам диагностический overhead тоже искажает p.

## 5. Снять диагностику перед честным A/B

```sh
git apply --reverse --check patches/performance/0017-npc-lag-breakdown.patch
git apply --reverse patches/performance/0017-npc-lag-breakdown.patch
```

Пересобрать без 0017, повторить тот же переход несколько раз в каждой сборке. Для дальнейшего расследования полезны: состав патчей, VM/heap/CPU clock/settings, старый lag, обе строки профиля одного перехода и несколько непрофилированных пиков. Ни новые FPS, ни новый результат PSPKVM агентом заранее не обещаются.
